# ChinaConnect Internationalization (i18n) Guide

## Goal

Every visitor sees their own language. 12 supported: `en`, `ja`, `ko`, `zh-CN`, `zh-TW`, `th`, `vi`, `ru`, `fr`, `de`, `ar`, `fa`.
**No English fallback**: a missing key fails CI; nothing ships unless every language has a translation.

## Source of truth

- `src/i18n/translations.ts` — the bundled runtime dictionary; this is what the browser actually uses
- `en-translations.json` and `<lang>-translations.json` — the human-readable flat dot-key source files

### Workflow

1. Add or change a string in `en-translations.json` first.
2. Run `node gen-missing.mjs <lang>` (or `all`) to translate.
3. Run `node merge-i18n.mjs` to rebuild `translations.ts`.
4. Run `pnpm check:i18n` to verify coverage.

### Adding a new key

```
echo '{"foo.bar": "Hello"}' >> en-translations.json.tmp
```
or open `en-translations.json` and add the dot-key.

Then translate:
```
node gen-missing.mjs all        # all 11 non-en languages
node gen-missing.mjs th         # just Thai
```

Then rebuild:
```
node merge-i18n.mjs
pnpm check:i18n
```

### Adding a new language

1. Add the language to `SUPPORTED_LANGUAGES` in `src/i18n/translations.ts` and `Language` type union.
2. Add it to `scripts/check-i18n.mjs` `SUPPORTED` array.
3. Add a `<lang>-translations.json` (empty `{}` is fine to start).
4. Run `node gen-missing.mjs <lang>` then `node merge-i18n.mjs`.
5. Run `pnpm check:i18n`.

## Using translations in the UI

### Static HTML (`[data-i18n]`)

```astro
<h1 data-i18n="home.heroTitle">Your trusted guide to exploring China</h1>
```

For attributes:
```astro
<input data-i18n-placeholder="auth.emailPlaceholder" placeholder="you@example.com" />
<button data-i18n-aria="common.menu" aria-label="Menu">…</button>
<a data-i18n-title="tooltips.mapTip" title="View on the map">…</a>
```

Placeholders / values can use `{var}`:
```json
"cityPage.intro": "Welcome to {city}, one of China's most fascinating destinations."
```

### Server-side (Astro components)

```astro
---
import { translations } from "@/i18n/translations";
import { getLangFromUrl } from "@/i18n/utils";

const lang = getLangFromUrl(Astro.url);
const t = translations[lang] || translations.en;
const title = t.home?.pageTitle ?? translations.en.home.pageTitle;
---
<BaseLayout title={title} ...>
  <h1 data-i18n="home.heroTitle">{t.home?.heroTitle ?? translations.en.home.heroTitle}</h1>
</BaseLayout>
```

### React components

```tsx
import { useLanguage } from "@/i18n/context";
import { translations } from "@/i18n/translations";

const lang = useLanguage();
const t = translations[lang] || translations.en;
return <h1>{t.home?.heroTitle}</h1>;
```

### Switching language at runtime

`BaseLayout` already wires up `<select id="lang-switcher">` and runs:
1. `localStorage["chinaconnect_language"] = newLang`
2. `applyLangAttributes(newLang)` — sets `<html lang>` and `dir="rtl|ltr"`
3. `applyTranslationsTo(document)` — re-renders every `[data-i18n]`, `[data-i18n-placeholder]`, `[data-i18n-title]`, `[data-i18n-aria]`
4. Dispatches `languagechange` so React components can subscribe

For React, subscribe with:
```tsx
useEffect(() => {
  const fn = (e: CustomEvent) => setLang(e.detail);
  window.addEventListener("languagechange", fn as EventListener);
  return () => window.removeEventListener("languagechange", fn as EventListener);
}, []);
```

### City / blog names

City slugs: `city.<slug>.name` (12-language localized). Loaded via:
```ts
const localCityName = translations[lang]?.["city." + city.slug + ".name"]
                   ?? translations.en?.["city." + city.slug + ".name"]
                   ?? city.nameEn;
```

## Blog multi-language system

All blog posts live in `src/i18n/blog.ts`. The BlogRecord map must have the same slug list in every language.

### Adding a blog post

1. Add the slug to every language entry (12 copies). Each entry needs:
   - `slug` (must match across languages)
   - `title` (≥ 5 chars)
   - `description` (≥ 30 chars)
   - `date` (ISO `YYYY-MM-DD`)
   - `author`
   - `category` (one of `guide`, `food`, `travel`, `culture`, `city`, `announcement`)
   - `tags` (array of strings)
   - `body` (Markdown, ≥ 200 chars)
   - `readingMinutes` (number)

2. Run `pnpm check:i18n` — it validates that every slug is present in every language.

### Rendering blog posts

```astro
import { listBlogPosts, getBlogPost } from "@/i18n/blog";
const lang = getLangFromUrl(Astro.url);
const posts = listBlogPosts(lang);
const post = getBlogPost(lang, params.slug);
```

When a slug is missing for the current language, the loader falls back to `blogPosts.en`. CI still fails until the language entry exists.

## CI enforcement

`pnpm check:i18n` runs in CI before build. It:
- Parses every language block in `src/i18n/translations.ts`
- Verifies every `en` baseline key exists in every language
- Verifies every key referenced via `data-i18n="…"` / `t("…")` / `i18nKey="…"` exists in `en` baseline
- For `src/i18n/blog.ts`, verifies every language has the same slug list

If any check fails, the build aborts.

## Locale-prefixed city routes

City detail pages use two route trees because Astro is configured with
`prefixDefaultLocale: false`:

- English remains under `src/pages/city/**` and renders as `/city/<slug>/`.
- The other 11 languages live under `src/pages/[lang]/city/**` and render as
  `/<lang>/city/<slug>/`.
- Each localized city route returns all supported language and city
  combinations from `getStaticPaths`, producing localized HTML during the
  Astro build rather than relying on browser-side replacement.
- `functions/[[path]].ts` fetches the locale-prefixed static asset first and
  only falls back to the unprefixed URL when that localized asset does not
  exist. Do not restore unconditional locale-prefix stripping.

This routing architecture shipped in `ffd2730` and `b86a436`. The complete
35-city, 11-non-English-language content set was generated and committed in
`f4ce425`. Validate future changes with both `pnpm build` and
`node scripts/verify-launch.mjs`; HTTP-only checks should also be supplemented
with localized-content sampling because a `200` response can still contain an
English fallback page.

## Forbidden

- Hardcoded English strings in `src/pages/**` or `src/components/**`
- `translations.en.xx ?? ""` patterns that silently fall back to English
- Translating proper nouns (city official names, brand names) inconsistently across languages — use the `city.<slug>.name` keys for cities
